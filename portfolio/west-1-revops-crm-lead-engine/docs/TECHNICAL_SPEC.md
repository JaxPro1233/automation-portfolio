# Техническое задание

## WEST 1 — Revenue Operations / CRM Lead Engine

**Статус:** версия 2.0, реализовано и готово к развёртыванию
**Тип проекта:** deployment-ready production automation with safe demo mode
**Основной язык интерфейсов и материалов:** английский
**Язык технической документации:** русский

## 1. Назначение системы

Создать систему обработки входящих лидов, которая принимает заявки из нескольких каналов, приводит данные к единому формату, предотвращает дубли, квалифицирует лид, назначает ответственного менеджера, сохраняет результат в CRM, уведомляет менеджера и контролирует соблюдение SLA.

Система должна демонстрировать не только успешный сценарий, но и эксплуатационную надежность: идемпотентность, повторные попытки, обработку ограничений API, журналирование, очередь неуспешных событий и восстановление после ошибок.

## 2. Бизнес-цели и измеримый результат

Система должна:

1. исключать создание повторных контактов и сделок при повторной доставке одного события;
2. регистрировать валидного лида в CRM не позднее 60 секунд после приема webhook в штатном режиме;
3. автоматически назначать активного менеджера по формальным правилам;
4. уведомлять менеджера сразу после успешного создания или обновления CRM-записи;
5. обнаруживать лиды, не взятые в работу в пределах SLA;
6. не терять события при временной недоступности внешнего API;
7. позволять проследить судьбу каждого события по единому `event_id`;
8. давать воспроизводимое публичное демо без клиентских данных и обязательных платных аккаунтов.

## 3. Пользователи и роли

| Роль | Возможности |
|---|---|
| Lead | Отправляет заявку через форму или внешний источник |
| Sales manager | Получает назначенного лида, открывает CRM и меняет статус обработки |
| Sales lead | Получает эскалации по просроченному SLA и видит очередь необработанных лидов |
| Administrator | Настраивает источники, правила scoring/routing, менеджеров и SLA |
| Operator / developer | Анализирует журналы, повторяет failed events и проверяет интеграции |
| Portfolio viewer | Запускает безопасный сценарий и просматривает результат без рабочих credentials |

## 4. Границы MVP

### 4.1. В MVP входит

- прием лидов из двух источников:
  - форма сайта;
  - симулятор Meta Lead Ads с совместимым webhook payload;
- проверка подлинности/секрета webhook, если источник ее поддерживает;
- валидация и нормализация входных данных;
- идемпотентная обработка события;
- поиск дублей по нормализованному email и телефону;
- создание либо обновление контакта и сделки;
- детерминированный lead scoring;
- AI-резюме оценки с безопасным fallback;
- назначение менеджера по территории, услуге и round-robin;
- fallback owner при отсутствии подходящего активного менеджера;
- уведомление в Slack или сохранение preview в деморежиме;
- контроль первого действия менеджера по SLA;
- напоминание и одна эскалация;
- постановка неготового лида в простую nurture-очередь;
- retries с учетом `Retry-After`;
- журнал событий и отдельная очередь failed events;
- повторная обработка failed event оператором;
- synthetic fixtures и воспроизводимый demo-сценарий.

### 4.2. В MVP не входит

- реальная отправка Meta Lead Ads;
- массовые email- или SMS-рассылки;
- двусторонняя синхронизация всей CRM;
- обучение собственной ML-модели scoring;
- production SSO/RBAC;
- полноценный BI-dashboard;
- обработка платежных, медицинских или иных специальных категорий данных;
- автоматическое удаление production-данных по юридическим запросам;
- поддержка нескольких CRM одновременно в одном запуске.

## 5. Режимы работы

### 5.1. Demo mode — обязательный

Использует synthetic data, mock CRM adapter и notification preview. Не требует реальных токенов и не выполняет внешних отправок. Должен быть режимом по умолчанию.

### 5.2. Integration mode — опциональный

Использует HubSpot test/free account и Slack test workspace. Активируется только явными переменными окружения и после добавления credentials вне Git.

Оба режима используют одинаковую бизнес-логику и отличаются только реализациями адаптеров.

## 7. Архитектура

```text
Website form ──────┐
                   ├─ Webhook gateway ─ validation ─ inbox/idempotency
Meta simulator ────┘                                      │
                                                          v
                              normalize ─ dedupe ─ qualify/score
                                                          │
                                      routing ─ CRM adapter ─ notification
                                                          │
                                      SLA scheduler ─ reminder/escalation
                                                          │
                              event log / retries / failed-event queue
```

Архитектурные границы:

1. **Source adapters** преобразуют payload конкретного источника в канонический контракт.
2. **Inbox** сначала сохраняет принятое событие, затем запускает обработку.
3. **Business logic** не зависит от HubSpot, Slack или конкретной LLM.
4. **Outbound adapters** отвечают за внешние вызовы и единый формат ошибок.
5. **SLA worker** работает независимо от входящего webhook.
6. **Audit log** связывает все этапы одним `event_id` и `lead_id`.

```json
{
  "event_id": "evt_web_20260904_001",
  "event_type": "lead.submitted",
  "occurred_at": "2026-09-04T09:30:00Z",
  "source": "website",
  "source_event_id": "form_submission_1001",
  "lead": {
    "first_name": "Alex",
    "last_name": "Morgan",
    "email": " Alex.Morgan+demo@example.com ",
    "phone": "+1 (415) 555-0184",
    "company": "Northwind Studio",
    "territory": "US-WEST",
    "service": "crm_automation",
    "message": "We need to respond to inbound leads faster",
    "consent": true
  },
  "attribution": {
    "utm_source": "linkedin",
    "utm_medium": "paid_social",
    "utm_campaign": "revops_demo",
    "landing_page": "/crm-automation"
  }
}
```

Обязательные поля:

- `event_type`;
- `occurred_at`;
- `source`;
- `source_event_id`;
- хотя бы одно из `lead.email` или `lead.phone`;
- `lead.consent` для действий, предполагающих follow-up.

`event_id` может быть передан источником либо генерируется системой. Идемпотентность определяется прежде всего парой `source + source_event_id`, а не сгенерированным идентификатором.

## 9. Функциональные требования

### FR-01. Прием события

- Система предоставляет отдельные webhook endpoint для website и Meta simulator.
- На валидный запрос возвращается `202 Accepted` после надежного сохранения в inbox.
- Ответ содержит внутренний `event_id` и статус `accepted` либо `duplicate`.
- Невалидный JSON или неподдерживаемый `event_type` возвращает `400` без создания лида.
- Ошибка аутентификации источника возвращает `401` или `403`.

### FR-02. Идемпотентность события

- Уникальный ключ: `source + source_event_id`.
- Повторная доставка не создает новую сделку, контакт, assignment или уведомление.
- Повторный запрос возвращает ссылку на ранее созданное событие.
- Повторная обработка оператором использует исходную запись inbox и также остается идемпотентной.

### FR-03. Нормализация

- Email: trim, lowercase; исходное значение хранится отдельно.
- Для сопоставления Gmail-подобные `+tags` не удаляются глобально: поведение задается конфигурацией домена.
- Телефон преобразуется в E.164 при наличии достаточного country context.
- Если номер нельзя надежно нормализовать, исходное значение сохраняется, а поле получает признак `normalization_warning`.
- Пустые строки преобразуются в `null`.
- UTM и исходный source сохраняются неизменяемо как first-touch attribution; новые касания пишутся отдельно.

### FR-04. Валидация лида

- Должен присутствовать валидный email или телефон.
- Нельзя запускать follow-up без consent.
- Длина каждого свободного текстового поля ограничивается конфигурацией; HTML очищается.
- Невалидный лид получает статус `REJECTED`, код причины и запись в audit log.

### FR-05. Поиск дублей и merge

Порядок поиска:

1. точное совпадение нормализованного email;
2. точное совпадение нормализованного телефона;
3. совпадение внешнего CRM ID, если он известен.

Правила:

- при одном точном совпадении обновляется существующий контакт;
- при совпадении email с одним контактом, а телефона с другим автоматический merge запрещен; событие отправляется в `MANUAL_REVIEW`;
- непустое новое значение не должно молча затирать подтвержденное значение — изменение фиксируется как новое касание и в audit log;
- новая заявка существующего контакта может создать новую сделку, только если нет открытой сделки по той же услуге в заданном dedupe window;
- рекомендуемый dedupe window сделки — 30 дней, значение конфигурируется.

### FR-06. Lead scoring

Score рассчитывается детерминированно в диапазоне 0–100. Начальная конфигурация:

| Условие | Баллы |
|---|---:|
| Корпоративный email | +15 |
| Указана компания | +10 |
| Целевая услуга `crm_automation` | +25 |
| Территория обслуживается | +15 |
| Сообщение содержит конкретную бизнес-задачу | +15 |
| Источник с высоким намерением (website/contact, Calendly-style) | +10 |
| Есть телефон и email | +10 |
| Территория не обслуживается | -30 |
| Нет consent для follow-up | -20 |

Классы:

- `HOT`: 70–100;
- `WARM`: 40–69;
- `COLD`: 0–39.

Система сохраняет score, версию правил и список сработавших факторов. LLM не рассчитывает баллы и не меняет класс; она только формирует резюме на основании факторов и сообщения лида. При недоступности AI используется детерминированный шаблон.

### FR-07. Routing

Порядок назначения:

1. отфильтровать только активных менеджеров;
2. выбрать менеджеров, поддерживающих территорию;
3. выбрать менеджеров, поддерживающих услугу;
4. исключить менеджеров, достигших лимита активных лидов;
5. среди оставшихся применить round-robin;
6. если кандидатов нет — назначить `fallback_owner` и записать причину.

Операция назначения должна выполняться транзакционно, чтобы два одновременных лида не нарушили round-robin. Решение сохраняет `routing_rule_version` и причины выбора.

### FR-08. CRM sync

- Сначала выполняется upsert контакта, затем upsert/создание сделки.
- В CRM передаются нормализованные контактные данные, source/UTM, score, class, owner и AI summary.
- Локально сохраняются `crm_contact_id`, `crm_deal_id`, URL карточки и время последней успешной синхронизации.
- Повторный вызов использует стабильный idempotency/external key, где API это позволяет.
- Ответ API валидируется до фиксации успешного статуса.

### FR-09. Уведомление менеджера

Уведомление содержит:

- имя и компанию;
- телефон/email согласно настройкам masking;
- источник и кампанию;
- score и класс;
- краткие факторы оценки;
- AI summary или fallback summary;
- назначенного owner;
- ссылку на CRM;
- deadline первого действия.

Уведомление отправляется только после успешной CRM sync. Повторная обработка события не создает второе уведомление того же типа тому же получателю.

### FR-10. Статусы лида и сделки

Минимальные статусы обработки лида:

```text
RECEIVED → VALIDATED → QUALIFIED → ROUTED → SYNCED → NOTIFIED
    ├──────────────→ REJECTED
    ├──────────────→ MANUAL_REVIEW
    └──────────────→ FAILED

NOTIFIED → IN_PROGRESS → QUALIFIED_OPPORTUNITY
         ├────────→ NURTURE
         ├────────→ DISQUALIFIED
         └────────→ SLA_BREACHED
```

`FAILED` является техническим статусом события, а не бизнес-статусом контакта. Повторная обработка может вывести событие из `FAILED` без создания дублей.

### FR-11. Контроль SLA

- SLA отсчитывается от `accepted_at` до первого подтвержденного действия менеджера.
- Значения по умолчанию:
  - `HOT`: напоминание через 10 минут, эскалация через 30 минут;
  - `WARM`: напоминание через 30 минут, эскалация через 120 минут;
  - `COLD`: напоминание через 4 часа, эскалация через 1 рабочий день.
- Для demo допускается time compression, например 10 секунд и 30 секунд.
- Первым действием считается переход в `IN_PROGRESS` или более поздний бизнес-статус, полученный через webhook/polling CRM либо demo endpoint.
- Scheduler не должен создавать повторные reminder/escalation для одного SLA checkpoint.
- Неактивный owner до первого действия запускает переназначение на fallback owner.

### FR-12. Nurture

- В `NURTURE` можно перевести лид класса `COLD`/`WARM` либо лид с явным статусом «не сейчас».
- При отсутствии consent система сохраняет статус, но не создает outbound action.
- В MVP nurture action представляет собой запланированную запись/preview, а не реальную массовую отправку.
- Повторный входящий запрос контакта отменяет устаревший nurture action и запускает новую квалификацию.

### FR-13. Ошибки, retries и failed events

- Повторять только временные ошибки: timeout, network error, HTTP `408`, `429`, `500`, `502`, `503`, `504`.
- Уважать `Retry-After`, если заголовок присутствует.
- Иначе применять exponential backoff с jitter.
- Максимум 5 попыток для одного внешнего действия.
- Остальные `4xx` не повторять автоматически.
- После исчерпания попыток создать/обновить failed event с payload reference, шагом, кодом ошибки, количеством попыток и `next_action`.
- Секреты и полный чувствительный payload не должны попадать в error message.
- Оператор может повторить failed event после исправления причины.

### FR-14. Audit и поиск

- Каждый значимый переход статуса создает append-only audit entry.
- По `event_id`, `lead_id`, `source_event_id`, email hash или phone hash можно найти цепочку обработки.
- Audit entry содержит actor (`system`, `manager`, `operator`), timestamp, action и безопасные metadata.

## 10. Модель данных

Минимальный состав таблиц PostgreSQL:

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `lead_events` | Inbox входящих событий | `id`, `source`, `source_event_id`, `payload`, `status`, timestamps |
| `contacts` | Канонические контакты | `id`, original/normalized email/phone, company, consent |
| `contact_touchpoints` | История источников и обращений | `contact_id`, `event_id`, attribution, message |
| `deals` | Локальное представление сделки | `id`, `contact_id`, service, stage, score, owner_id, CRM IDs |
| `score_results` | Версионированный расчет | `deal_id`, `score`, `class`, `rule_version`, factors |
| `sales_owners` | Менеджеры и доступность | territory, services, capacity, active, notification target |
| `routing_assignments` | История назначений | `deal_id`, owner, reason, rule_version |
| `sla_checkpoints` | Reminder/escalation | `deal_id`, type, due_at, completed_at, delivery status |
| `outbound_actions` | Notification/nurture previews | type, recipient, idempotency key, status |
| `integration_attempts` | Попытки внешних вызовов | adapter, operation, attempt, response class, timing |
| `failed_events` | Dead-letter queue | event/step, error code, attempts, resolution status |
| `audit_log` | Неизменяемая история | entity, action, actor, safe metadata, timestamp |

Ограничения уникальности:

- `lead_events(source, source_event_id)`;
- нормализованный email и телефон индексируются, но merge-конфликт обрабатывается явно;
- `outbound_actions(idempotency_key)`;
- `sla_checkpoints(deal_id, checkpoint_type, schedule_version)`;
- внешние CRM IDs уникальны в пределах CRM adapter.

## 11. Нефункциональные требования

### Надежность

- Ни одно принятое (`202`) событие не может существовать только в памяти workflow.
- Все внешние side effects идемпотентны либо защищены локальным idempotency key.
- Перезапуск n8n/worker не должен приводить к потере или повторной отправке действия.

### Производительность MVP

- Webhook acknowledgement: p95 не более 2 секунд после сохранения события.
- End-to-end до CRM в штатном режиме: p95 не более 60 секунд.
- Минимальная демонстрационная нагрузка: 100 событий за 5 минут без дублей и потерь.

### Наблюдаемость

- Structured logs содержат `event_id`, `lead_id`, `deal_id`, workflow/step и результат.
- Метрики: accepted, rejected, duplicate, processed, failed, retry count, CRM latency, notification latency, SLA breaches.
- Dashboard не обязателен; достаточно SQL views и машиночитаемого summary для demo.

### Поддерживаемость

- Правила scoring, routing и SLA не зашиваются в несколько несогласованных workflow.
- Все адаптеры имеют единый интерфейс и mock-реализацию.
- Схема БД создается миграциями.
- Workflow export хранится без credentials.

## 12. Безопасность и приватность

- Никаких токенов, webhook secrets и реальных персональных данных в Git.
- `.env.example` содержит только имена переменных и безопасные значения.
- Raw payload доступен только технической роли и имеет срок хранения, задаваемый конфигурацией.
- В логах email и телефон маскируются; для поиска используются hash-поля.
- В AI передается только минимальный набор данных. Телефон, полный email и технические identifiers модели не нужны.
- Prompt и AI response считаются недоверенными данными; AI не управляет routing, score или отправкой.
- Demo fixtures используют только вымышленные имена, компании, домены и номера.
- Webhook имеет rate limit и ограничение размера body.

## 14. Обязательные тестовые сценарии

1. Валидный website lead создает контакт, сделку, assignment и одно уведомление.
2. Повтор того же `source_event_id` не создает новых сущностей или side effects.
3. Новый event с тем же email обновляет существующий контакт.
4. Телефон в разных форматах сопоставляется с одним контактом.
5. Лид только с email успешно обрабатывается.
6. Лид только с телефоном успешно обрабатывается при достаточном country context.
7. Email и телефон указывают на разные контакты — `MANUAL_REVIEW`, автоматического merge нет.
8. Неактивный назначенный менеджер заменяется fallback owner.
9. Два одновременных лида корректно проходят round-robin.
10. AI недоступен — score сохраняется, используется fallback summary.
11. CRM отвечает `429` с `Retry-After` — запрос повторяется не раньше указанного времени.
12. CRM отвечает `503`, затем `200` — событие завершается успешно без дубля сделки.
13. CRM отвечает постоянным `400` — автоматического retry нет, создается failed event.
14. После пяти временных ошибок событие появляется в failed queue.
15. Ручной replay после исправления ошибки завершает исходное событие без дублей.
16. Необработанный HOT lead вызывает одно напоминание и одну эскалацию.
17. Действие менеджера до deadline отменяет будущую эскалацию.
18. Лид без consent не создает nurture outbound action.
19. HTML/script во входном сообщении очищается и не исполняется.
20. Логи и exports не содержат токены и открытые контактные данные.

## 15. Критерии приемки

Проект считается принятым, если одновременно выполнены условия:

- оба источника принимают fixtures через документированные endpoints;
- повторная отправка одного payload доказуемо не создает дубль;
- contact/deal dedupe работает по нормализованным email и телефону;
- scoring воспроизводим, сохраняет факторы и не зависит от ответа LLM;
- routing учитывает territory, service, capacity, active flag и fallback;
- CRM adapter создает/обновляет сущности и возвращает стабильную ссылку;
- уведомление создается один раз и только после CRM sync;
- SLA reminder и escalation воспроизводятся в ускоренном demo;
- временные ошибки проходят bounded retry, постоянные ошибки попадают в failed queue;
- операторский replay не создает повторных side effects;
- все обязательные тестовые сценарии автоматизированы и проходят;
- `README` позволяет новому пользователю запустить demo по шагам;
- репозиторий не содержит credentials, клиентских данных или ложных production-утверждений;
- n8n workflow экспортирован выключенным и не отправляет реальные сообщения по умолчанию.

## 16. Сценарий портфолио-демо

Целевая длительность видео: 60–120 секунд.

1. Открыть архитектурную схему и одной фразой назвать бизнес-проблему.
2. Отправить HOT lead через website form.
3. Показать нормализованную запись, score/factors и выбранного owner.
4. Показать mock CRM card и Slack preview.
5. Отправить тот же payload повторно и показать `duplicate` без новых записей.
6. Сымитировать `429 → 200` и показать retry log.
7. Включить ускоренный SLA и показать reminder/escalation.
8. Завершить экраном с trace одного `event_id` от webhook до результата.

## 19. Допущения, зафиксированные для первой версии

- Основная CRM — HubSpot; GoHighLevel можно добавить позже отдельным adapter.
- Основной канал уведомлений — Slack.
- PostgreSQL является источником технической истины для inbox, idempotency, retries и SLA; CRM остается бизнес-системой учета контактов и сделок.
- В публичном demo реальные сообщения и внешние записи выключены.
- UI администратора не строится: настройки первой версии хранятся в конфигурации и seed-данных.
- Рабочие часы и праздники в MVP не моделируются полностью; `COLD` SLA «1 рабочий день» в первой версии допускает конфигурируемый календарный эквивалент и должен быть отмечен как ограничение.
